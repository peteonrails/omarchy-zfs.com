Why does ZFS on Omarchy need a package?

Omarchy assumes btrfs or ext4 with the Limine bootloader. On a ZFS root, three things quietly go wrong — each one ends in an unbootable or un-updatable system. omarchy-zfs turns each failure into a guarantee, enforced by pacman hooks on every transaction.

Boot-safety guarantee

omarchy update overwrites the mkinitcpio HOOKS drop-in with a zfs-less version, so the next initramfs can't mount your root. A PostTransaction hook runs last in every transaction, re-asserts the zfs hook, and regenerates the initramfs + ZFSBootMenu.

Update-survivability guarantee

Omarchy's installer leaves a btrfs-hardcoded snapper config behind. On ZFS it makes omarchy update abort before touching a single package — permanently. The snapper guard removes stale non-btrfs configs (and keeps doing so as Omarchy re-creates them).

Boot-order guarantee

Limine is a hard dependency of Omarchy and can silently move itself above ZFSBootMenu in the EFI BootOrder — a dead boot on ZFS. The boot-order guard keeps ZFSBootMenu first after every transaction, without ever deleting another bootloader's entry.

What you get

Everything is a real, package-owned file — nothing dangles in /usr/local, and omarchy update can never silently strip the ZFS layer.

Install

Already running Omarchy on a ZFS root

Install the package; the hooks take over from there. ZFSBootMenu itself is a soft dependency — install it from the AUR or use the prebuilt EFI images.

yay -S omarchy-zfs

Fresh machine

Use the omarchy-zfs ISO — the stock Omarchy installer built with a root-on-ZFS path (pool + datasets + ZFSBootMenu, encryption optional). Build it yourself in one command from the repo.

Migrating an existing btrfs/ext4 Omarchy install

Possible with a second disk or backup/restore: replicate your data, bootstrap the pool with omarchy-bootstrap-zfs, restore, install omarchy-zfs. See the README for the full procedure and safety notes.

Note: the AUR also lists a third-party package named omarchy — it's an unrelated placeholder. The real omarchy dependency is satisfied by the official package every Omarchy system already has installed from pkgs.omarchy.org.

FAQ

Is this a fork of Omarchy?

No. omarchy-zfs is a regular Arch package that depends on stock Omarchy (Quattro and later). You keep normal omarchy update behavior and the official package channel; this package just makes those updates ZFS-safe.

Which kernel / ZFS packages does it work with?

Any provider of the virtual zfs and zfs-utils packages: zfs-dkms, zfs-dkms-git, zfs-linux, or zfs-linux-lts. The kernel guard blocks upgrades that would out-run your ZFS module's supported kernel range, so you never boot a kernel ZFS can't build for.

What happens to snapper and Limine?

They stay installed (they're Omarchy dependencies) but inert: btrfs-only snapper configs are cleaned so updates don't abort, limine/snapper timers are masked, and the boot-order guard keeps ZFSBootMenu first. Nothing is force-removed, and genuine btrfs pools keep working snapper coverage.

Does it support native ZFS encryption?

Yes. ZFSBootMenu prompts for the key at boot via the included unlock hook, themed to match Omarchy.

Can I hibernate on ZFS?

Yes — omarchy-zfs-hibernation-setup creates a zvol swap sized to your RAM and wires up the resume path. omarchy-zfs-hibernation-available reports whether your system qualifies.

How do I roll back a bad update?

Reboot into ZFSBootMenu, pick the automatic pre-upgrade snapshot taken right before the transaction, and boot it. From there you can promote it permanently with omarchy-zfs-snapshot restore.
